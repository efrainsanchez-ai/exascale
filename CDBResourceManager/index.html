Overview

This chapter implements CDB-level Oracle Database Resource Manager to protect a two-node Exadata Exascale CDB from noisy-neighbor PDBs. A CDB resource plan allocates resources among PDBs; each PDB can then use its own PDB resource plan to allocate its assigned portion among sessions.

The example has twelve PDBs: PDB01–PDB04 are Platinum, PDB05–PDB08 are Gold, and PDB09–PDB12 are Silver. Shares express priority only when PDBs contend: Platinum uses 4 shares per PDB, Gold 2, and Silver 1. The tier totals are therefore 16, 8, and 4 shares (57%, 29%, and 14% of the 28-share pool). The contention order is Platinum first, Gold second, and Silver third: Gold has twice the per-PDB shares of Silver. Platinum can borrow idle capacity up to 99%. Gold has a 60% hard ECPU-capacity ceiling and Silver a 40% hard ceiling, including when higher tiers are idle.

The cluster has two VMs with 8 enabled ECPUs and 33 GB RAM each. Treat 16 enabled ECPUs (2 VMs × 8 enabled ECPUs) and 66 GB RAM as planning capacity, not a promise that one PDB can use a cluster-wide fixed amount. An ECPU is Oracle's abstracted, elastic compute allocation from the Exascale compute pool; it is not a fixed one-to-one equivalent of a physical core, OCPU, or vCPU. CDB plans are enforced by the database instances, so validate service placement and per-instance demand in RAC. The stated 12 additional reserved ECPUs are held for future scale-up and are not active capacity for this plan.

Interpreting the observed 80% VM memory usage

This snapshot still matters for the 12-PDB plan: 5.4 GiB available is below the workbook's 6 GB combined provisional root/background plus OS/transient allowance. Treat it as a warning to collect a time series during representative workload before increasing PDB PGA limits. Correlate free -h with GV$SGA, GV$PGASTAT, and operating-system process memory; do not allocate the apparent buff/cache amount to Oracle by assumption.

ECPU capacity basis

Scope Enabled ECPU capacity Planning meaning
Per VM 8 enabled ECPUs The local capacity basis for a RAC instance.
Two-VM cluster 16 enabled ECPUs Aggregate planning capacity (2 × 8), not a single-instance entitlement.
Additional reserved ECPUs / VM 12 reserved ECPUs Supports the stated 33 GB RAM allocation for that VM and future ECPU scale-up; exclude the reserved ECPUs from active compute planning until they are enabled.
Additional reserved ECPUs / two-VM cluster 24 reserved ECPUs 2 VMs × 12 reserved ECPUs; reservation capacity only, not active ECPU capacity for this plan until enabled.

Resource Manager percentages are relative limits, not guaranteed ECPU assignments. For example, a 60% PDB ECPU-capacity limit constrains that PDB relative to the active capacity on an instance; it does not reserve 60% of the 16-ECPU cluster for the PDB. Keep RAC services balanced and validate the result on each VM.

Additional reserved ECPUs are physically held for each VM and are the basis for the stated 33 GB RAM allocation on each node: each VM has 12 reserved ECPUs, or 24 reserved ECPUs across the two-node cluster. Exascale adds VM memory according to the total ECPU reservation, not only the enabled ECPUs. The reserved ECPUs are not active for compute licensing or this plan's active ECPU capacity until enabled.

To scale up, open the VM cluster in the OCI Console, select Scale VM Cluster, increase ECPUs enabled per VM by the required multiple of four without exceeding the total reserved ECPUs, then save the change and monitor the update to AVAILABLE. Enabling already reserved ECPUs avoids a full restart or relocation. If further capacity is needed beyond the reservation, add ECPUs to the reservation in units of four; Oracle performs this expansion using a rolling restart as ECPUs are added.

Capacity policy

Tier PDBs Shares / PDB ECPU-capacity limit / PDB Parallel-server limit / PDB Suggested PDB PGA guardrail
Platinum PDB01–PDB04 4 99% 99% 3 GB PGA limit
Gold PDB05–PDB08 2 60% 60% 2 GB PGA limit
Silver PDB09–PDB12 1 40% 40% 1 GB PGA limit

Shares determine relative priority only while PDBs contend: the 4:2:1 per-PDB ratio gives Platinum first priority, Gold second, and Silver third. Platinum can borrow idle capacity up to its 99% limit. Gold and Silver remain constrained by their respective 60% and 40% ECPU-capacity and parallel-server ceilings, even when a higher tier is idle; those caps are intentional noisy-neighbor protection, not reservations.

The PGA values are per-PDB hard limits for a 33 GB VM, not reservations. Across all twelve PDBs on a VM, the PGA-limit envelope is 24 GB: Platinum uses 12 GB, Gold 8 GB, and Silver 4 GB. This workbook does not set PDB SGA_TARGET; measure existing SGA use separately before increasing a PGA tier or recalculating the combined memory budget.

Per-VM memory consumer Planning allowance Rationale
12 PDB PGA limits 24 GB 12 GB Platinum plus 8 GB Gold plus 4 GB Silver; limits are not reservations.
CDB root and Oracle background processes Up to 3 GB (provisional) A planning guardrail, not an Oracle Database 26ai (23.26.2) default or validated requirement. Keep it only when measured per-instance root/background demand and its peak leave sufficient headroom.
Operating system and transient headroom 3 GB Prevents PDB session growth, patching activity, and short-lived allocations from exhausting the 33 GB VM.
Total 33 GB Per-VM planning envelope.

Oracle Database 26ai Release Update 23.26.2 does not publish a fixed CDB-root-and-background memory requirement for an 8-ECPU VM. Therefore, 3 GB cannot be validated as a universal value; it is a provisional planning envelope, not a product default. It is not an instruction to set a CDB-root PGA parameter to 3 GB. Measure each RAC instance during representative workload and maintenance windows. If the observed root/background demand plus safety margin exceeds 3 GB, reduce the planned PDB PGA envelope before applying PDB limits.

Validate the provisional CDB-root allowance

SQL
Objective: verify the installed Oracle AI Database release and capture per-instance SGA and PGA evidence before accepting the 3 GB provisional root/background allowance.
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

SELECT banner_full
FROM   v$version
WHERE  banner_full LIKE 'Oracle Database%';

COLUMN inst_id FORMAT 999 HEADING 'INST'
COLUMN sga_mb FORMAT 9999990 HEADING 'SGA_MB'
SELECT inst_id,
       ROUND(SUM(value) / 1024 / 1024) AS sga_mb
FROM   gv$sga
GROUP BY inst_id
ORDER BY inst_id;

COLUMN pga_stat FORMAT A28
COLUMN pga_mb FORMAT 9999990 HEADING 'PGA_MB'
SELECT inst_id,
       name AS pga_stat,
       ROUND(value / 1024 / 1024) AS pga_mb
FROM   gv$pgastat
WHERE  name IN ('total PGA allocated', 'maximum PGA allocated')
ORDER BY inst_id, name;

Interpretation: these views report total instance SGA and PGA, not an isolated CDB-root-only allocation. Use them with operating-system memory telemetry and repeat the capture during root-heavy operations such as backup, patching, statistics maintenance, and PDB open/close activity. Retain the 3 GB allowance only when the observed per-instance evidence and a documented safety margin fit within it.

Back up root memory configuration

The backup card below creates local timestamped SPFILE and PFILE copies under /home/oracle/backup so you have a readable rollback artifact before changing memory parameters.

Bash
Objective: Create the backup directory and save timestamped SPFILE and PFILE copies before updating PDB-level memory parameters. Run this as the Oracle software owner with `ORACLE_SID` set for the target database.
wb07_card01() {
  if [[ -z "${ORACLE_SID:-}" ]]; then
    clear
    printf 'STOP: Set ORACLE_SID for the target database before creating backups.\n'
    return 1
  fi

  local backup_dir="$HOME/backup"
  local backup_stamp
  backup_stamp="$(date +%Y%m%d_%H%M%S)"
  mkdir -p "$backup_dir" || return 1

  local spfile_backup="$backup_dir/spfile_${ORACLE_SID}_${backup_stamp}.ora"
  local pfile_backup="$backup_dir/init${ORACLE_SID}_${backup_stamp}.ora"

  sqlplus -s / as sysdba <<SQL
WHENEVER SQLERROR EXIT SQL.SQLCODE
CREATE SPFILE='${spfile_backup}' FROM SPFILE;
CREATE PFILE='${pfile_backup}' FROM SPFILE;
EXIT
SQL

  clear
  printf '%-14s | %s\n' 'ARTIFACT' 'PATH' \
    'SPFILE backup' "$spfile_backup" \
    'PFILE backup' "$pfile_backup"
  printf '\n%s\n' 'wb07_card01'
}

Memory guardrails

The CDB plan controls ECPU and parallel-server allocation. PGA guardrails are configured separately inside each PDB. PGA_AGGREGATE_TARGET is the automatic-tuning target; PGA_AGGREGATE_LIMIT is the hard per-PDB session-memory ceiling. This workbook does not change SGA parameters.

The combined PDB memory-limit envelope may be intentionally over-provisioned because PDBs do not consume memory up to their limits at all times. This is a capacity-control model, not a reservation model. However, long-running reports, batch jobs, large sorts, parallel operations, or runaway sessions can consume large amounts of PGA for extended periods. Monitor real memory usage across the CDB, RAC instances, PDBs, and operating system, then adjust the limit values when observed workload behavior shows the envelope is too high or too restrictive.

Tier PDB count PGA target / PDB PGA limit / PDB Tier PGA-limit total
Platinum 4 1,500 MB 3 GB 12 GB
Gold 4 1 GB 2 GB 8 GB
Silver 4 256 MB 1 GB 4 GB
12 PDBs 12 — — 24 GB

The 24 GB PGA-limit envelope is a capacity guardrail, not pre-reserved memory. Validate it against measured SGA demand, the provisional root/background allowance, operating-system use, and transient headroom before applying changes.

5. Display current PDB PGA parameters

SQL
Objective: Display every open user PDB and show whether PGA values are local or inherited from root.
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

COLUMN pdb_name FORMAT A14 HEADING 'PDB_NAME'
COLUMN pga_target_mb FORMAT A18 HEADING 'PGA_TARGET_MB'
COLUMN pga_limit_mb FORMAT A18 HEADING 'PGA_LIMIT_MB'
COLUMN value_source FORMAT A14 HEADING 'VALUE_SOURCE'

WITH open_pdbs AS (
  SELECT con_id, name
  FROM   v$containers
  WHERE  con_id > 2
  AND    open_mode = 'READ WRITE'
), parameter_rows AS (
  SELECT con_id, name, value
  FROM   CONTAINERS(v$system_parameter)
  WHERE  name IN ('pga_aggregate_target', 'pga_aggregate_limit')
), root_values AS (
  SELECT MAX(CASE WHEN name = 'pga_aggregate_target' THEN value END) AS pga_target,
         MAX(CASE WHEN name = 'pga_aggregate_limit'  THEN value END) AS pga_limit
  FROM   v$system_parameter
  WHERE  name IN ('pga_aggregate_target', 'pga_aggregate_limit')
), effective_values AS (
  SELECT o.name AS pdb_name,
         COALESCE(MAX(CASE WHEN p.name = 'pga_aggregate_target' THEN p.value END), r.pga_target) AS pga_target,
         COALESCE(MAX(CASE WHEN p.name = 'pga_aggregate_limit'  THEN p.value END), r.pga_limit) AS pga_limit,
         CASE WHEN COUNT(p.value) = 0 THEN 'INHERITED' ELSE 'LOCAL' END AS value_source
  FROM   open_pdbs o
  CROSS JOIN root_values r
  LEFT JOIN parameter_rows p ON p.con_id = o.con_id
  GROUP BY o.name, r.pga_target, r.pga_limit
)
SELECT pdb_name,
       CASE
         WHEN REGEXP_LIKE(pga_target, '^[0-9]+(\.[0-9]+)?G$', 'i') THEN TO_CHAR(ROUND(TO_NUMBER(REGEXP_SUBSTR(pga_target, '^[0-9]+(\.[0-9]+)?')) * 1024, 0)) || ' MB'
         WHEN REGEXP_LIKE(pga_target, '^[0-9]+(\.[0-9]+)?M$', 'i') THEN TO_CHAR(ROUND(TO_NUMBER(REGEXP_SUBSTR(pga_target, '^[0-9]+(\.[0-9]+)?')), 0)) || ' MB'
         WHEN REGEXP_LIKE(pga_target, '^[0-9]+$') THEN TO_CHAR(ROUND(TO_NUMBER(pga_target) / POWER(1024, 2), 0)) || ' MB'
         ELSE pga_target
       END AS pga_target_mb,
       CASE
         WHEN REGEXP_LIKE(pga_limit, '^[0-9]+(\.[0-9]+)?G$', 'i') THEN TO_CHAR(ROUND(TO_NUMBER(REGEXP_SUBSTR(pga_limit, '^[0-9]+(\.[0-9]+)?')) * 1024, 0)) || ' MB'
         WHEN REGEXP_LIKE(pga_limit, '^[0-9]+(\.[0-9]+)?M$', 'i') THEN TO_CHAR(ROUND(TO_NUMBER(REGEXP_SUBSTR(pga_limit, '^[0-9]+(\.[0-9]+)?')), 0)) || ' MB'
         WHEN REGEXP_LIKE(pga_limit, '^[0-9]+$') THEN TO_CHAR(ROUND(TO_NUMBER(pga_limit) / POWER(1024, 2), 0)) || ' MB'
         ELSE pga_limit
       END AS pga_limit_mb,
       value_source
FROM   effective_values
ORDER BY pdb_name;
Output

PDB_NAME       PGA_TARGET_MB      PGA_LIMIT_MB       VALUE_SOURCE
-------------- ------------------ ------------------ --------------
PDB01          2500 MB            10240 MB           INHERITED

7. Stop, start, and check PDB01 from SQL*Plus

This stop/start process can be used to force application sessions and connection pools to disconnect and reconnect to the PDB. Use it only during an approved maintenance or validation window, because active sessions are interrupted and pools must create fresh database connections after the PDB is reopened.

Run this from CDB$ROOT as a common administrator. The INSTANCES=ALL clause applies the PDB state change across all RAC instances.

SQL
Objective: Close, reopen, and check PDB01 across all RAC instances from SQL*Plus.
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

COLUMN inst_id FORMAT 999 HEADING 'INST'
COLUMN pdb_name FORMAT A14 HEADING 'PDB_NAME'
COLUMN open_mode FORMAT A12 HEADING 'OPEN_MODE'

SHOW CON_NAME

ALTER PLUGGABLE DATABASE PDB01 CLOSE IMMEDIATE INSTANCES=ALL;

SELECT inst_id,
       name AS pdb_name,
       open_mode
FROM   gv$pdbs
WHERE  name = 'PDB01'
ORDER  BY inst_id;

ALTER PLUGGABLE DATABASE PDB01 OPEN READ WRITE INSTANCES=ALL;

SELECT inst_id,
       name AS pdb_name,
       open_mode
FROM   gv$pdbs
WHERE  name = 'PDB01'
ORDER  BY inst_id;

Best practices

  • Capacity priority: Shares apply only while PDBs contend; they are priorities, not reservations. Platinum can use idle capacity up to its 99% limit; Gold and Silver remain capped at 60% and 40%.
  • Hard ceilings: Treat utilization_limit and parallel_server_limit as deliberate per-PDB protection boundaries. Change a limit only after capacity testing and owner approval.
  • PGA envelope: The 24 GB combined PDB PGA-limit envelope is not reserved memory. Validate it against measured SGA demand, the provisional root/background allowance, and OS/transient headroom before increasing any PDB limit.
  • PGA relationship: Keep PGA_AGGREGATE_TARGET at or below one-half of its PDB PGA_AGGREGATE_LIMIT; lower-tier PDBs must not receive larger PGA limits because they temporarily use idle ECPU capacity.
  • RAC placement and testing: Balance services across both RAC nodes, then load-test tiers alone and together before tuning shares or limits from AWR/ASH evidence.
